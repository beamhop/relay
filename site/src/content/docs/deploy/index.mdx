beamhop is one process that serves everything on one port (3334 by default): the Nostr relay, the Blossom media server, the admin app and plugin routes. So whichever method you pick, you end up with the same thing: one program, one port, and a place to keep its data.

  <Card title="Docker & Compose" icon="seti:docker">

<Aside type="note" title="What's prebuilt">
The Node bundle is prebuilt on every push to `main` and runs with `npx` from GitHub. beamhop is not published to npm, and there are no published Docker images or release binaries yet: those methods start from a `git clone` of [the repository](https://github.com/beamhop/relay) and build locally, which only takes a few minutes.
</Aside>

## Which one should I pick?

- **Just want to try it?** Run it with [npx](/relay/deploy/node/#run-it-with-npx). One command, nothing to build.
- **Not sure?** Use [Docker Compose](/relay/deploy/docker/). It handles restarts, health checks and graceful shutdown for you.
- **You want the smallest footprint** on a plain VPS: build the [single binary](/relay/deploy/binary/) and run it under systemd.
- **You're developing** a plugin or the admin app: run [from source with Bun](/relay/deploy/bun/).

All methods run the same code and read the same configuration, so you can switch later. Your data moves with you: copy the database and blob folder, or use [export and import](/relay/deploy/backups-upgrades/#move-events-between-relays).

## What every deployment needs

However you run it, a public relay needs the same few things. Each has its own page:

1. **A public address.** Set `BEAMHOP_PUBLIC_URL` to the `https://` address people will use. Logins and media links depend on it.
2. **An owner**, so someone can sign in to the admin app (`BEAMHOP_OWNERS=npub1…`).
3. **A [reverse proxy](/relay/deploy/reverse-proxy/)** in front for TLS and WebSockets.
4. **Persistent storage**: SQLite on a local disk (the default) or [PostgreSQL](/relay/deploy/postgres/), plus a folder or [S3-compatible bucket](/relay/deploy/s3/) for media.
5. **[Backups](/relay/deploy/backups-upgrades/)** and **[monitoring](/relay/deploy/monitoring/)**.

The [production checklist](/relay/deploy/production-checklist/) puts all of this on one page.

## How configuration works

You can configure beamhop with a `beamhop.config.json` file, `BEAMHOP_*` environment variables or command-line flags. Later sources win: defaults, then the file, then environment variables, then flags. These pages mostly use environment variables because they work the same everywhere.

Only boot-time things (ports, database, storage, proxy trust) are set this way. Most relay behaviour, like limits, relay info, access rules and upload sizes, is changed live in the admin app and stored in the database.
