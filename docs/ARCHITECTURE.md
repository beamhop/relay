# beamhop architecture

beamhop is a Nostr relay with a built-in Blossom media server, a PWA admin panel and a plugin system.
Bun is the primary runtime; everything must also run on Node ≥ 22 (via `bun build --target=node`).

## Packages (Bun workspaces, scope `@beamhop/*`)
| Package | Responsibility |
|---|---|
| `sdk` | **Contracts only** (+ tiny runtime: EventBus, HookRegistry, logger, zod config schemas). Everyone depends on it. |
| `storage` | `createStores(config) → Stores`: SQL `Db` abstraction (bun:sqlite / better-sqlite3 / postgres), EventStore (FTS for NIP-50), users, invites, ip rules, kv, audit, `createSettingsService`. |
| `core` | `createRelay(deps) → RelayEngine`: NIP-01 protocol, validation pipeline, subscriptions/fan-out, NIP-09/11/13/40/42/45/50/62/70/77/29/05/17-59, rate limits, moderation policies, retention jobs. |
| `blossom` | `createBlossom(deps) → BlossomService`: BUD-01/02/04/06/08/11/12, FS & S3 blob drivers, opt-in EXIF strip, thumbnails (sharp, optional), quotas, moderation status. |
| `metrics` | `createMetrics(deps) → MetricsService`: bus collectors, rollups in DB, live snapshot, GeoIP, OpenTelemetry export, process stats. |
| `admin-api` | `createAdminApi(deps) → AdminApi`: REST at `/admin/api` per `sdk/src/admin-contract.ts`, auth (NIP-98 / password / passkeys), RBAC, audit, SSE, web push, NIP-86. |
| `admin-ui` | React + shadcn/ui + TanStack Router/Query + MapLibre PWA. Built with Vite to `packages/admin-ui/dist`, served at `/admin`. |
| `server` | Composition root: config loading, runtime adapters (Bun.serve / node:http + ws), plugin manager, CLI, Docker, binary + node builds. |
| `plugins/*` | First-party/example plugins built with `@beamhop/sdk` `definePlugin`. |

## Request routing (server)
1. `GET /` with `Upgrade: websocket` → `relay.handleConnection`
2. `POST /` with `Content-Type: application/nostr+json+rpc` → `adminApi.nip86`
3. `relay.http` (NIP-11 on `GET /` with `Accept: application/nostr+json`, `/.well-known/nostr.json`)
4. `/admin/api/*` → admin-api; `/admin/*` → admin-ui static (SPA fallback to index.html)
5. `/plugins/<name>/*` → plugin public routes
6. blossom `app` (`/upload`, `/list/:pubkey`, `/mirror`, `/<sha256>[.ext]`)
7. `GET /` (browser) → simple landing page with relay info

## Event write pipeline (core)
IP rules (block/allow CIDRs) and connection caps are enforced when the WebSocket connects, not per event. `connectionsPerIp` applies per address; an IPv6 /64 may hold 4× that in total (one subscriber's prefix, or a whole LAN behind SLAAC). Rate-limit buckets key IPv6 by /64. Every inbound message (except CLOSE / NEG-CLOSE) first takes a token from a per-connection and per-address bucket, so floods are refused before any signature check or query. Relay staff and allow-listed IPs are exempt; users with a rate-limit override get a per-connection limit raised by their override and no per-address bucket (an override of 0, meaning unlimited, exempts them like staff). A connection may have at most 100 EVENTs awaiting their OK (1000 for staff, allow-listed IPs and override users) and authenticate at most 10 pubkeys.

parse (filter arrays capped at 5000 values each and per filter) → size limits → id/sig verify (id recomputed; verified (id, pubkey, sig) cached) → created_at bounds → NIP-40 expiration → NIP-13 PoW → pubkey deny/ban, NIP-62 vanished, mute (shadow) → access mode (public / whitelist / invite / auth-required, NIP-42; non-members may only send inbox kinds 1/4/6/7/16/1059/1111/9735 that p-tag a member) → NIP-70 protected → duplicate (an already-stored event is answered `duplicate:` before anyone's rate limit is charged, so replaying someone's signed events can't drain their allowance) → rate limit (per IP, and per pubkey — per pubkey *and* address unless the connection is NIP-42-authenticated as the author; IPv6 per /64) → **plugin write hooks** (`hooks.runWrite`) → built-in content policy (kind allow/block, word/regex filters; a regex filter's worst-case backtracking is bounded statically and it only scans as much leading content — 1–8 KiB — as keeps that bound within a fixed step budget) unless plugin said `accept` → special kinds (5 deletion and 62 vanish run before storing, skipped for an already-stored event; 1984 report → bus, then (after the OK, serialized per reported pubkey) the NIP-56 auto-ban check: non-member reports return at once, member reporters are tracked in kv per reported pubkey (seeded once from its recent reports); NIP-29 group kinds 9000-9022) → store (or ephemeral) → NIP-62 re-check (an event that raced a vanish request is removed again) → NIP-29 state change (only for an event stored as new; each control event applies at most once, recorded in `core_group_applied` as part of the state change and released if it fails — the event is then removed again so a retry can apply it) → fan-out to matching subscriptions (respecting `hooks.isVisible` & NIP-42 gated kinds like 1059/4) → bus `event.accepted` / `event.rejected`.

NIP-29 specifics: group control events from clients, sync and plugins must be recent (10 min) and relay-signed 39000-39009 events are only accepted from the relay itself / admin / import; invite codes (9009) are readable only by the group's admins/moderators and are stored hashed; closed groups need a valid code to join directly (failed attempts are limited per group and per address, valid ones aren't counted), open groups ignore unknown codes; hidden groups answer outsiders as if they didn't exist and hide their control events; a deleted group is hidden from everyone before its events are purged.

COUNT and NIP-77 NEG-OPEN apply the same visibility rules as REQ: built-in privacy rules (gated kinds, private groups, hidden group metadata / control events, invite codes) and, when a plugin registers a visibility hook, the hook too. The main count / id list is taken before the hidden set, so an event stored in between is never disclosed. Hidden events are found by listing candidate ids (never whole events) and loading them in ~4 MB batches for the visibility check (at most 5000 private candidates for the built-in rules). With a plugin visibility hook, COUNT and NEG-OPEN list the candidate ids and check them one by one in batches (up to 50k; 1000 for search counts) and answer exactly; a count that can't be computed is refused (never `approximate`). Negentropy: 2 sessions per connection, 4 NEG-OPENs prepared at once relay-wide and 2 per address (more wait up to 3 s for a slot), a relay-wide item budget, compact session storage, NEG-MSG traffic rate-limited; any NEG-ERR ends its session, and expired sessions (5 min) are swept relay-wide every 30 s and whenever the budget runs out.

A REQ delivers the newest `limit` events *visible to the connection*: when a filter can match events it may not see (gated kinds, private groups, a plugin visibility hook) and hidden ones filled part of the page, older pages are read until `limit` visible events are found (at most 5000 extra rows per REQ), so the result count doesn't reveal how many hidden events exist.

Stored REQ results honour backpressure like live delivery: sending pauses while the client's buffer is above 512 KiB (half the 1 MiB level where live events start being dropped), and a client that doesn't drain within 10 s is disconnected (EOSE is never dropped).

Read throttling: REQ/COUNT/NEG-OPEN share a per-connection and per-address bucket whose burst is capped at 120 (480 per address), so a minute's allowance can't run back to back. NIP-50 search (a synchronous full-text query on SQLite) additionally has small per-connection/per-address buckets and query-time budgets (ms of search per minute, per address and relay-wide): an estimate (recent average query time) is charged when a search is admitted, so queued searches count too, and settled against the actual time afterwards. Searches run one at a time relay-wide, each after a loop turn, and take their search slot before a relay-wide query slot, so searches waiting their turn never hold slots plain REQs need; their `limit` is clamped to 100. A connection runs at most 3 stored queries or COUNTs (incl. streaming their results) at once, others wait; materialized-but-unsent results are budgeted per connection (32 MB), per address (64 MB) and relay-wide (384 MB), and a REQ that would exceed them is CLOSED `rate-limited:`. Stored results are paced to keep the client's send buffer under half the level where live events start being dropped. Staff are exempt from the buckets, not from the concurrency limits. Hard caps a retry can't fix (filter values per connection) are CLOSED `restricted:`, transient ones `rate-limited:`.

SQLite: search queries pin the FTS index as the outer loop (a fresh database has no planner stats), 1-2 character ASCII terms aren't prefix-expanded (non-ASCII ones are: the tokenizer keeps CJK runs as one token), and `PRAGMA optimize` runs hourly. A transaction's statements run on the single connection; anything else waits, including work a finished transaction left behind. Invalid stored runtime settings are dropped field by field (array elements individually); any invalid `access.*` field locks all of access down (whitelist + auth required for reads and writes), as does a stored blob that isn't an object. The critical alert is recorded in the audit log and emitted again once the server has started (when admin/metrics/plugin listeners exist).

## Conventions
- TypeScript, ESM, strict. Packages export `./src/index.ts` directly (no build step for libs).
- **Runtime-neutral code**: use Web APIs (`fetch`, `Request`, `crypto.subtle`, `TextEncoder`) and `node:*` modules. Bun-only APIs (`bun:sqlite`, `Bun.serve`) only behind `isBun` checks with dynamic `import()`.
- SQL: write portable SQL with `?` placeholders via `Db`; each package owns its tables via `db.migrate("<namespace>", migrations)`; table names prefixed by package (`blossom_*`, `metrics_*`, `admin_*`, `core_*`). JSON stored as TEXT, booleans as INTEGER, timestamps unix seconds.
- Cross-package communication: only through sdk interfaces, `EventBus` and `HookRegistry`. Never import another package's internals.
- Tests: `bun test` with files in `packages/<pkg>/test/*.test.ts`. Use SQLite `:memory:`.
- Typecheck: `npx tsc --noEmit -p tsconfig.json` (admin-ui has its own tsconfig).
