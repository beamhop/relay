# beamhop architecture

beamhop is a Nostr relay with a built-in Blossom media server, a PWA admin panel and a plugin system.
Bun is the primary runtime; everything must also run on Node ≥ 22 (via `bun build --target=node`).

## Packages (Bun workspaces, scope `@beamhop/*`)
| Package | Responsibility |
|---|---|
| `sdk` | Contracts at the package root (+ tiny runtime: EventBus, HookRegistry, logger, zod config schemas). Shared runtime-neutral helpers several packages must apply identically live in subpath exports `@beamhop/sdk/<name>` (`config`, `net`, `media-policy`, `search`, `secrets`, `regex-safety`, `util`), never re-exported from the root, not part of the plugin API stability promise. Everyone depends on it. |
| `storage` | `createStores(config) → Stores`: SQL `Db` abstraction (bun:sqlite / better-sqlite3 / postgres), EventStore (FTS for NIP-50), users, invites, ip rules, kv, audit, `createSettingsService`. |
| `core` | `createRelay(deps) → RelayEngine`: NIP-01 protocol, validation pipeline, subscriptions/fan-out, NIP-09/11/13/40/42/45/50/62/70/77/29/05/17-59, rate limits, moderation policies, retention jobs. |
| `blossom` | `createBlossom(deps) → BlossomService`: BUD-01/02/04/06/08/11/12, FS & S3 blob drivers, opt-in EXIF strip, thumbnails (sharp, optional), quotas, moderation status. |
| `metrics` | `createMetrics(deps) → MetricsService`: bus collectors, rollups in DB, live snapshot, GeoIP, OpenTelemetry export, process stats. |
| `admin-api` | `createAdminApi(deps) → AdminApi`: REST at `/admin/api` per `sdk/src/admin-contract.ts`, auth (NIP-98 / password / passkeys), RBAC, audit, SSE, web push, NIP-86. |
| `admin-ui` | React + shadcn/ui + TanStack Router/Query + MapLibre PWA. Built with Vite to `packages/admin-ui/dist`, served at `/admin`. |
| `server` | Composition root: config loading, runtime adapters (Bun.serve / node:http + ws), plugin manager, CLI, Docker, binary + node builds. |
| `plugins/*` | First-party/example plugins built with `@beamhop/sdk` `definePlugin`. |

## Request routing (server)
1. `GET /` with `Upgrade: websocket` → `relay.handleConnection`
2. `POST /` with `Content-Type: application/nostr+json+rpc` → `adminApi.nip86`
3. `relay.http` (NIP-11 on `GET /` with `Accept: application/nostr+json`, `/.well-known/nostr.json` — answered only for the `nip05.domain` or publicUrl host when a domain is set)
4. `GET /health` (readiness: 503 with `status` `starting` / `draining` / `stopping` / `stopped`, or when the database doesn't answer within 2 s); `GET /health/live` (liveness, used by the Docker HEALTHCHECK); `GET /metrics` (Prometheus: bearer token; with no token set, only loopback peers without forwarding headers, and nobody when `server.trustProxy` is on)
5. `/admin/api/*` → admin-api; `/admin/plugins-ui/<name>.js` → running plugins' UI bundles; `/admin/*` → admin-ui static (SPA fallback to index.html). Admin HTML is served with a CSP whose `script-src` is `'self'` plus the inline-script hashes; same-origin user content is neutralized where it is served (Blossom and the admin raw-media route serve JavaScript as `text/plain` and refuse `Sec-Fetch-Dest` script/worker/XSLT loads), and plugin routes are trusted code
6. `/plugins/<name>/*` → plugin public routes
7. blossom `app` (`/upload`, `/list/:pubkey`, `/mirror`, `/<sha256>[.ext]`)
8. `GET /` (browser) → simple landing page with relay info

## Admin API
Sessions are random ids stored as SHA-256 hashes (HttpOnly, SameSite=Strict cookie). Every POST/PUT/PATCH/DELETE that isn't NIP-98 authenticated — logins included — needs `X-Requested-With: beamhop` or an `Origin` equal to the public origin, and a JSON body (NDJSON for `/events/import`, capped at 256 MiB). The admin API never reads forwarding headers itself: the server adapter resolves the client IP using `server.trustedProxies`. Moderation is ranked: below owner nobody can delete, ban, mute, hide or block the events or blobs of a peer or superior (a blob is protected by its highest-ranked uploader), deleting a user who has a role needs `admins.manage`, and NIP-86 event bans record the banner's role (lifting one needs at least that rank; banning an id that isn't stored needs owner). Banned event ids live in the database and are re-read every ~5 s, so every instance sharing it enforces them; if they can't be loaded, writes are checked against the database one by one and refused if that fails too. Removing a role or deleting a user wipes their password, TOTP, passkeys, sessions and push devices. Bulk actions audit every target; destructive actions are audited in a `finally` with what was actually done (partial counts, `error`), and a users bulk action stops after a 20 s budget or a client disconnect, answering `remaining` for the targets not touched. Moderation actions (ban, unban, IP rules, user delete, admin-access revocation) go through `ModerationService`, shared by REST, bulk actions, report resolution, NIP-86 and the CLI; every ban also removes the user from the allow list. Event bans are owned by `BannedEventService` (its write hook lives from admin-api start to stop; `GET /events/bans`, `DELETE /events/bans/:id`). The reports queue is an index table (`admin_report_index`) kept current on `report.created` and status changes, backfilled once from stored kind-1984 events and pruned when reports are deleted, so listing, totals and the open count cover every report (no recent-reports window a flood could push real reports out of). Report and alert pushes are coalesced (first at once, the rest as one digest per minute, alerts per level and title); deliveries run at most 8 at a time with a 15 s timeout, a device refused 5 times in a row (400/401/403) is dropped, and push endpoints resolving to private or the host's own addresses are refused. SSE: at most 8 streams per admin, one shared authorization recheck, each message serialized once. Every request schema is tied to its `admin-contract` type (`Same<>`). Audit log retention: `retention.auditLogDays` (0 = keep forever).

Plugin settings are masked for viewers and in audit records by one shared JSON-schema walker (`maskSecretValues` in sdk) that follows `properties`, `items`, `prefixItems`, `additionalProperties`, `anyOf`/`oneOf`/`allOf` and local `$ref`s; a value is secret if any branch marks it (`format: "password"`, `writeOnly`, `x-secret`) or its key name looks like a credential. Plugin enable/disable/settings changes are audited once, by the admin API, with the request IP.

## Event write pipeline (core)
IP rules (block/allow CIDRs) and connection caps are enforced when the WebSocket connects, not per event. `connectionsPerIp` applies per address; an IPv6 /64 may hold 4× that in total (one subscriber's prefix, or a whole LAN behind SLAAC) and a /48 `connectionsPerIpv6Site` (default 16 × `connectionsPerIp`); `maxConnections` optionally caps the relay as a whole (allow-listed IPs exempt). Rate-limit buckets key IPv6 by /64. Every inbound message (except CLOSE / NEG-CLOSE up to 2 KiB) first takes a token from a per-connection and per-address bucket — read off the raw frame's type before any JSON parsing, so floods (compressed frames included) are refused before parse, signature check or query; a connection refused more than 3× its limit within a minute is disconnected. Relay staff and allow-listed IPs are exempt; users with a rate-limit override get a per-connection limit raised by their override and no per-address bucket (an override of 0, meaning unlimited, exempts them like staff). A connection may have at most 100 EVENTs awaiting their OK (1000 for staff, allow-listed IPs and override users) and authenticate at most 10 pubkeys.

parse (filter arrays capped at 5000 values each and per filter) → size limits → id/sig verify (id recomputed; verified (id, pubkey, sig) cached) → created_at bounds → NIP-40 expiration → NIP-13 PoW → pubkey deny/ban, NIP-62 vanished, mute (shadow) → access mode (public / whitelist / invite / auth-required, NIP-42; non-members may only send inbox kinds 1/4/6/7/16/1059/1111/9735 that p-tag a member) → NIP-70 protected → duplicate (an event already stored, or an ephemeral event relayed in the last 5 minutes, is answered `duplicate:` before anyone's rate limit is charged, so replaying someone's signed events can't drain their allowance or re-deliver their ephemeral traffic) → rate limit (per IP, and per pubkey — per pubkey *and* address unless the connection is NIP-42-authenticated as the author; IPv6 per /64) → **plugin write hooks** (`hooks.runWrite`) → built-in content policy (kind allow/block, word/regex filters; a regex filter's worst-case backtracking is bounded statically: content up to the pattern's input limit (1–8 KiB) is tested in one run within a fixed step budget, and the rest of a longer post is scanned in overlapping windows for at most one more budget — cheap patterns such as literals cover the whole post, backtracking-prone ones stop when the budget is spent; the admin panel's preview uses the same matcher; the `report` action accepts the event, raises an alert and, when everyone may read the event, files a relay-signed kind-1984 report in the Reports queue (carrying the event's `h` tags; never for DMs, gift wraps or private/hidden group content)) unless plugin said `accept` → special kinds (5 deletion and 62 vanish run before storing, skipped for an already-stored event; 1984 report → bus, then (after the OK, serialized per reported pubkey) the NIP-56 auto-ban check: non-member reports return at once, member reporters are tracked in kv per reported pubkey (seeded once from its recent reports), reports signed by the relay key never count, and an auto-ban disconnects the user; NIP-29 group kinds 9000-9022) → store (or ephemeral) → NIP-62 re-check (an event that raced a vanish request is removed again) → NIP-29 state change (only for an event stored as new; each control event applies at most once, recorded in `core_group_applied` as part of the state change and released if it fails — the event is then removed again so a retry can apply it) → fan-out to matching subscriptions (respecting `hooks.isVisible` & NIP-42 gated kinds like 1059/4; the event is serialized once per broadcast) → bus `event.accepted` / `event.rejected`. A failing post-store step (e.g. publishing relay-signed group metadata) is logged and doesn't turn the accepted event into an error.

Plugin hooks have time budgets (write and query 2 s, blob 30 s, overridable per registration) and receive an AbortSignal. On timeout a write hook fails open (as `next`), query and blob hooks fail closed (CLOSED / 503); a thrown error fails closed for every kind. Timeouts raise a coalesced `alert` and count in `hook_incidents_total`. Hook lists are copy-on-write: enabling or disabling a plugin never changes the hooks an in-flight event runs through.

Deletions by people who can't post: a NIP-62 request to vanish addressed to this relay always takes effect, whatever the author's status (it skips PoW, bans, access mode, plugin hooks and content policy), but has its own per-address limit (10/min) and the duplicate check; the request itself is only stored and relayed when it deleted something or set a marker, its author isn't banned, deny-listed or muted, it has at most 1 KiB of content and 64 tags, and it passes the content policy. Lasting vanish markers are capped at 100k. A kind 5 from a banned, deny-listed or muted author is applied and answered OK but neither stored nor relayed.

NIP-11 advertises 5, 29 and 86 only while NIP-05, groups and the admin API are enabled. With `nip05.domain` set, `/.well-known/nostr.json` answers only requests whose `Host` or `X-Forwarded-Host` is that domain or the relay's own (publicUrl) host; the first refusal is logged with the host received.

NIP-29 specifics: group creation is limited to 10/h per pubkey and 40/h per address (staff exempt); a 9005 deletion tombstones what it removes, so the deleted messages can't be republished; `previous` references (at most 50) must point at events the author can read, matched by id against the group's newest ~100 and the relay's newest ~500 events of the last 24 h; group control events from clients, sync and plugins must be recent (10 min) and relay-signed 39000-39009 events are only accepted from the relay itself / admin / import; invite codes (9009) are readable only by the group's admins/moderators and are stored hashed; closed groups need a valid code to join directly (failed attempts are limited per group and per address, valid ones aren't counted; a join request without one is stored and relayed through the normal pipeline but answered OK false `restricted:`), open groups ignore unknown codes; hidden groups answer outsiders as if they didn't exist and hide their control events; a deleted group is hidden from everyone before its events are purged. Group state changes are written to the database first (one transaction per change) and only then applied in memory, one change at a time per group, so a failed write never leaves memory ahead of the database.

COUNT and NIP-77 NEG-OPEN apply the same visibility rules as REQ: built-in privacy rules (gated kinds, private groups, hidden group metadata / control events, invite codes) and, when a plugin registers a visibility hook, the hook too. The main count / id list is taken before the hidden set, so an event stored in between is never disclosed. Hidden events are found by listing candidate ids (never whole events) and loading them in ~4 MB batches for the visibility check (at most 5000 private candidates for the built-in rules). With a plugin visibility hook, COUNT and NEG-OPEN list the candidate ids and check them one by one in batches (up to 50k; 1000 for search counts) and answer exactly; a count that can't be computed is refused (never `approximate`). Negentropy: 2 sessions per connection, 4 NEG-OPENs prepared at once relay-wide and 2 per address (more wait up to 3 s for a slot), a relay-wide item budget (ids count against it while they are being listed), ids listed in 50k pages straight into compact typed-array storage (a sync with more than 50k events in a single second is refused), NEG-MSG traffic rate-limited; any NEG-ERR ends its session, and expired sessions (5 min open, or 60 s idle) are swept relay-wide every 30 s and whenever the budget runs out.

A REQ delivers the newest `limit` events *visible to the connection*: when a filter can match events it may not see (gated kinds, private groups, a plugin visibility hook) and hidden ones filled part of the page, older pages are read until `limit` visible events are found (at most 5000 extra rows per REQ), so the result count doesn't reveal how many hidden events exist.

Stored REQ results honour backpressure like live delivery: sending pauses while the client's buffer is above 512 KiB (half the 1 MiB level where live events start being dropped), and a client that doesn't drain within 10 s is disconnected (EOSE is never dropped).

Read throttling: REQ/COUNT/NEG-OPEN share a per-connection and per-address bucket whose burst is capped at 120 (480 per address), so a minute's allowance can't run back to back. NIP-50 search (a synchronous full-text query on SQLite) additionally has small per-connection/per-address buckets and query-time budgets (ms of search per minute, per address and relay-wide): an estimate (recent average query time) is charged when a search is admitted, so queued searches count too, and settled against the actual time afterwards. Searches run one at a time relay-wide, each after a loop turn, and take their search slot before a relay-wide query slot, so searches waiting their turn never hold slots plain REQs need; their `limit` is clamped to 100. Every search filter, live-only `limit:0` ones included, adds 500 to the connection's filter weight (20,000), so a connection holds about 39 of them; search terms are parsed once per subscription and event content lowercased once per broadcast. A connection runs at most 3 stored queries or COUNTs (incl. streaming their results) at once, others wait; materialized-but-unsent results are budgeted per connection (32 MB), per address (64 MB) and relay-wide (384 MB), and a REQ that would exceed them is CLOSED `rate-limited:`. Stored results are paced to keep the client's send buffer under half the level where live events start being dropped. Plain (non-search) REQ/COUNT/NEG-OPEN store time is measured and charged to query-time budgets too (15 s per minute per address, 45 s relay-wide); reads are refused `rate-limited:` while a budget is in debt. The live subscription index is capped relay-wide by `maxTotalFilterWeight`. Staff are exempt from the buckets, not from the concurrency limits. Hard caps a retry can't fix (filter values per connection) are CLOSED `restricted:`, transient ones `rate-limited:`.

SQLite: search queries pin the FTS index as the outer loop (a fresh database has no planner stats), 1-2 character ASCII terms aren't prefix-expanded (non-ASCII ones are: the tokenizer keeps CJK runs as one token), and `PRAGMA optimize` runs hourly. Query shapes (SQLite only; Postgres keeps the generic statement): a small `kinds` or `authors` list (2–50 values) with a `limit` runs as a UNION ALL of per-value index scans, and a filter with a single-value tag condition is driven from `event_tags` ordered by its `created_at` (which must always equal the event's). Bulk deletes (expiry purge, retention, delete by pubkey / filter / ids, per-author trims) run in adaptive batches (~50 ms each) with a timer turn in between, so they never stall connections; they are not atomic as a whole. A transaction's statements run on the single connection; anything else waits, including work a finished transaction left behind. A watchdog warns about a transaction open 5 s and rolls it back at 60 s (`TxAbortedError`; its late statements reject); transactions over 20 ms yield a timer turn after committing. Never await non-database work inside `db.tx`. `users.event_count` is the lifetime number of accepted events (never decremented); retention uses it only to pick candidates and counts what is stored. Invalid stored runtime settings are dropped field by field (array elements individually); any invalid `access.*` field locks all of access down (whitelist + auth required for reads and writes), as does a stored blob that isn't an object. The critical alert is recorded in the audit log and emitted again once the server has started (when admin/metrics/plugin listeners exist).

## Lifecycle and shutdown
Phases: `starting` → `ready` → `draining` → `stopping` → `stopped`. Shutdown (SIGTERM/SIGINT, `beamhop.stop()`) runs inside `server.shutdownTimeoutMs` (default 10 s; a second signal exits at once):
1. **drain** (≤ 5 s): new HTTP requests get 503 + `Retry-After` (except `/health*`, `/metrics`), WebSocket upgrades 503; in-flight requests (counted in `beamhop.fetch`) finish; the relay answers new messages "error: relay is shutting down" and finishes every queued EVENT (each gets an OK — none is dropped), the scheduler stops starting jobs and awaits running ones (they get an AbortSignal), admin-api ends SSE streams, Blossom refuses new uploads, plugin jobs are awaited, tracked background tasks (`TaskTracker`, `deps.tasks`) settle;
2. **relay stop** (≤ 1 s): close 1001, close handshakes;
3. plugins teardown, then admin-api / Blossom / metrics stop (final metrics flush);
4. **db.close** last: waits (≤ 3 s) for queued statements and the open transaction, later calls reject with `DbClosedError`.
Each step races its own deadline and logs what overran. Background work started off a request path must go through the tracker. Crash policy: an `uncaughtException` shuts down gracefully and exits 1; an `unhandledRejection` is logged with its stack, counted and alerted (coalesced), and more than 10 in a minute shut down too (`handleProcessErrors: false` opts out for embedders). A WebSocket handler that throws closes that connection with 1011.

## Server, metrics, plugins
The relay key lives in kv `server/relaySecretKey` (or config), created insert-if-absent so instances starting together on one database agree; core refuses to start without `relaySecretKey`. Metrics keep at most 500 distinct (code, reason) rejection pairs per hour and count the rest as `(other)`. The spam-filter plugin's per-message, per-pubkey and role caches are LRU-capped. Metrics COUNT the stored events at most every 60 s (stored events are added in memory in between) and cache breakdowns over more than 24 h for 5 min. Plugins: import and setup are bounded to 30 s, teardown to 5 s; a timed-out or failed setup marks the plugin `error` and anything it registers afterwards is removed; disable/stop cancel a setup in progress; `enabled` is persisted only after setup succeeds; `ctx.bus` only allows `on` (removed on disable) and `emit("alert")`. Unknown config file keys and `BEAMHOP_*` variables are warned about at boot. Blossom: row changes run in one transaction and driver I/O happens after commit (bytes are deleted only on a positive "no row"; failed deletes are retried from `blossom_pending_deletes`); S3 requests have header timeouts, size-scaled PUT timeouts and retries; FS writes are fsynced and stale `.tmp` files swept at startup; a client abort is 499; `/list` is rate-limited per IP.

## Conventions
- TypeScript, ESM, strict. Packages export `./src/index.ts` directly (no build step for libs).
- **Runtime-neutral code**: use Web APIs (`fetch`, `Request`, `crypto.subtle`, `TextEncoder`) and `node:*` modules. Bun-only APIs (`bun:sqlite`, `Bun.serve`) only behind `isBun` checks with dynamic `import()`.
- SQL: write portable SQL with `?` placeholders via `Db`; each package owns its tables via `db.migrate("<namespace>", migrations)`; table names prefixed by package (`blossom_*`, `metrics_*`, `admin_*`, `core_*`). JSON stored as TEXT, booleans as INTEGER, timestamps unix seconds.
- Cross-package communication: only through sdk interfaces, `EventBus` and `HookRegistry`. Shared logic is imported from an sdk subpath, never copied and never imported from another package's `src/`. Each package's `test/` may import its own `src/` only; e2e imports packages by name. Drift guard: when two packages need the same rule (address classification, how a blob is served, search tokenization), it moves into an sdk subpath with its tests there, and a copy found later is replaced by an import rather than kept in sync.
- Tests: `bun test ./packages ./plugins` with files in `packages/<pkg>/test/*.test.ts`, named by feature (not by audit round). Use SQLite `:memory:`. CI (`.github/workflows/ci.yml`) runs typecheck, unit tests and the relay e2e suite on every push/PR, and the admin Playwright suite nightly.
- Typecheck: `bun run typecheck` (the root tsconfig plus admin-ui's own and its tests' tsconfigs).
